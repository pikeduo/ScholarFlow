# 阶段五：语义排序与智能核验

## 1. 阶段目标

本阶段实现 ScholarFlow 的核心排序和迭代搜索能力，将阶段四的 canonical 候选通过 BGE-M3、FAISS、bge-reranker-v2-m3 和 DeepSeek 逐步压缩、重排和核验，并通过 Coverage Gap Analyzer 驱动下一轮搜索。

完整链路：

```text
Canonical Candidates
→ 规则与 RRF 初排
→ BGE-M3 语义粗排
→ bge-reranker-v2-m3 重排
→ DeepSeek 逐项条件核验
→ 最终综合排序
→ Coverage Gap Analyzer
→ 继续搜索或返回约 20 篇论文
```

本阶段采用“本地语义排序 + LLM 条件核验”的混合方案，不进行模型微调和强化学习。

---

## 2. 前置条件

- 阶段四能够提供稳定 `paper_id`、摘要、来源、RRF 和过滤结果。
- 阶段三已有 `semantic_rank`、`verify_constraints`、`assess_coverage` 和 `evolve_query` 节点。
- 本地模型目录和 FAISS 数据目录可写。
- SQLite 已有 `embedding_records`、`index_metadata` 和 usage 表。
- 机器资源已确认，能够选择 CPU 或 GPU 模式。

---

## 3. 资源与模型策略

### 3.1 BGE-M3

用途：

- 中英文跨语言相似度。
- 候选粗排。
- 文献库语义搜索。
- 相似论文查询。
- 弱去重候选提示。

推荐通过 FlagEmbedding 或兼容封装加载，具体依赖在实现时固定版本。

### 3.2 bge-reranker-v2-m3

用途：

- 对 BGE-M3 Top 40–60 进行 Cross-Encoder 重排。
- 输出 Query 与论文文本对的相关性分数。

### 3.3 DeepSeek

- Flash：默认条件核验、覆盖缺口和结果解释。
- Pro：仅在复杂查询、Schema 连续失败或 Top-20 冲突时回退。

### 3.4 模型加载原则

- 首次使用时延迟加载。
- 模型路径配置化。
- 下载和加载输出日志。
- 由用户执行模型下载或首次运行。
- 服务启动不得强制联网下载模型。
- 模型不可用时有明确降级路径。
- 标准模式仅执行 DeepSeek 精排、约束核验和理由生成，强制跳过 BGE-M3 与 Cross Encoder 并按 RRF 传递候选；深度模式才允许执行 BGE-M3 和 Cross Encoder。`SCHOLARFLOW_SEMANTIC_RANKING_ENABLED` 与 `SCHOLARFLOW_CROSS_ENCODER_RANKING_ENABLED` 只控制深度模式是否允许相应本地模型，`SCHOLARFLOW_LLM_RANKING_ENABLED` 同时控制两种模式的 DeepSeek 精排。任何主动跳过都必须返回可展示摘要，不能伪装为模型故障或约束已满足。

## 4. 小阶段 5.1：文本构造器

### 4.1 PaperEmbeddingText

建议格式：

```text
Title: {title}
Keywords: {keywords}
Abstract: {abstract}
Venue: {venue}
Year: {year}
```

实现：

```python
class PaperTextBuilder:
    def build_embedding_text(self, paper: PaperRecord) -> BuiltText: ...
    def build_reranker_text(self, paper: PaperRecord) -> BuiltText: ...
```

### 4.2 规则

- 标题始终保留。
- 摘要超长时按模型长度和配置截断。
- 缺摘要时使用标题、关键词、venue 和年份。
- 不使用引用数影响文本语义。
- 不拼入完整来源 JSON。
- 构造文本需记录版本，例如 `paper_text_v1`。

### 4.3 查询文本

根据 QueryIntent 构造：

```text
Research topic: ...
Required methods: ...
Required datasets: ...
Tasks: ...
Exclusions: ...
```

`must_include` 放在主要位置，`should_include` 作为偏好，`exclude` 作为明确排除说明。

### 4.4 文本哈希

```text
SHA-256(model_name + model_revision + builder_version + text)
```

摘要或模型变化时自动失效。

## 5. 小阶段 5.2：BGE-M3 EmbeddingService

### 5.1 接口

```python
class EmbeddingService:
    async def encode_queries(self, texts: list[str]) -> EmbeddingBatch: ...
    async def encode_documents(self, texts: list[str]) -> EmbeddingBatch: ...
```

本地模型推理通常为同步计算，可通过受控线程池或进程池调用，避免阻塞 FastAPI 事件循环。

### 5.2 设备选择

配置：

```yaml
embedding:
  model_name: BAAI/bge-m3
  local_path: data/models/bge-m3
  device: auto
  batch_size_cpu: 4
  batch_size_gpu: 16
  max_length: 2048
  normalize: true
```

`auto` 策略：

1. 检查 CUDA 是否可用。
2. 检查显存是否达到配置门槛。
3. 否则使用 CPU。
4. 记录实际设备。

### 5.3 批处理

- 按 Token 长度分桶，减少 padding。
- 捕获显存不足。
- OOM 时减小 batch 重试一次。
- CPU 模式限制并发，避免占满系统。

### 5.4 输出

```python
class EmbeddingBatch(BaseModel):
    vectors: NDArray
    model_name: str
    model_revision: str | None
    dimension: int
    normalized: bool
    latency_ms: int
    device: str
```

### 5.5 缓存

- SQLite 保存 embedding 元数据。
- FAISS 保存索引向量。
- 是否额外保存原始向量文件可配置。
- 相同 text_hash 不重复编码。

## 6. 小阶段 5.3：FAISS IndexManager 完整实现

### 6.1 索引结构

```text
IndexIDMap2(IndexFlatIP)
```

全局索引：

```text
data/faiss/global_papers.index
```

文献库索引：

```text
data/faiss/library.index
```

### 6.2 vector_id

- 使用 SQLite 生成稳定 64 位整数 ID。
- 不使用 Python `hash()`，因为进程间不稳定。
- `embedding_records` 保存 `paper_id ↔ vector_id`。

### 6.3 添加流程

```text
SQLite PaperRecord
→ 生成文本和 text_hash
→ 检查 embedding_records
→ BGE-M3 批量编码
→ SQLite 预写 embedding 状态 pending
→ FAISS add_with_ids
→ 原子保存临时索引文件
→ 替换正式索引
→ SQLite 状态 active
```

### 6.4 查询流程

```text
Query Embedding
→ FAISS search Top-Kx
→ 返回 vector_id 和 score
→ SQLite 映射 paper_id
→ 过滤逻辑删除和失效向量
→ 补足 Top-K
```

Top-Kx 应略大于目标数量，避免删除过滤后不足。

### 6.5 更新和删除

- 摘要变化：标记旧向量 inactive，添加新向量。
- 删除论文：SQLite 逻辑删除，查询后过滤。
- 失效向量比例达到阈值时重建索引。
- 不在每次删除时重建整个索引。

### 6.6 保存安全

- 先写 `.tmp`。
- 写完后校验数量和维度。
- 使用原子替换。
- 保存前后记录日志。
- 进程内使用写锁，避免并发修改索引。

## 7. 小阶段 5.4：BGE-M3 粗排

### 7.1 输入

- 阶段四保留候选，建议不超过 180。
- QueryIntent。
- RRF 分数和规则匹配结果。

### 7.2 处理

1. 构造 Query 文本。
2. 获取 Query 向量。
3. 确保候选论文向量存在。
4. 计算余弦相似度。
5. 结合必要的标题精确命中奖励。
6. 排序并保留 40–60 篇。

### 7.3 分数

保存：

```python
class SemanticRankScore(BaseModel):
    paper_id: str
    dense_score: float
    title_match_bonus: float
    final_semantic_score: float
    embedding_model: str
    text_hash: str
```

标题奖励只用于小幅调整，不得覆盖明显较低的语义分数。

### 7.4 降级

BGE-M3 不可用时：

- 使用 RRF + 规则匹配进入 reranker 或 LLM 小集合。
- 限制候选数量。
- 标记 `semantic_rank_degraded`。

## 8. 小阶段 5.5：RerankerService

### 8.1 接口

```python
class RerankerService:
    async def rerank(
        self,
        query_text: str,
        papers: list[PaperRecord],
        top_k: int,
    ) -> list[RerankResult]: ...
```

### 8.2 输入规模

- 输入 40–60。
- 输出 20–40。
- 不对原始 200–300 篇运行 Cross-Encoder。

### 8.3 文本

Reranker 文本可比 Embedding 文本更精简：

```text
{title}\n{abstract}
```

附加年份和 venue 只在查询明确要求时加入。

### 8.4 批量和 OOM

- GPU 批处理。
- OOM 时 batch 减半重试一次。
- CPU 模式控制批量大小和并发。
- 输出模型版本和耗时。

### 8.5 降级

Reranker 失败时：

- 保留 BGE 排名。
- 继续 DeepSeek 核验。
- 记录降级原因。

## 9. 小阶段 5.6：Verification Schema

```python
class ConstraintEvidence(BaseModel):
    constraint: str
    status: Literal["true", "false", "unconfirmed"]
    evidence_field: Literal["title", "abstract", "keywords", "year", "venue", "metadata"]
    evidence_text: str | None

class PaperVerification(BaseModel):
    paper_id: str
    topic_match: str
    method_match: str
    dataset_match: str
    time_match: str
    must_results: list[ConstraintEvidence]
    should_results: list[ConstraintEvidence]
    exclude_results: list[ConstraintEvidence]
    relevance_level: Literal["high", "partial", "irrelevant"]
    confidence: float
    reason: str
```

`unconfirmed` 是合法结果，不能为了完整性强制改为 true 或 false。

## 10. 小阶段 5.7：DeepSeek 条件核验

### 10.1 批量策略

- 每批 5–10 篇。
- 实现默认每批 10 篇，单批请求超时 30 秒、最大输出 4,000 Token；查询规划仍使用独立超时。
- 单个批次失败时仅将该批论文按上游排序降级，继续执行其余批次并聚合成功批次的 Token；全部批次失败才执行完整 LLM 降级。
- 只发送标题、摘要、关键词、年份、venue 和必要来源。
- 不发送完整 API 原始响应。
- 每个候选带受控 `paper_id`。

### 10.2 Prompt 约束

- 只能使用提供的证据。
- 不允许补充外部知识。
- 无证据输出 `unconfirmed`。
- 输出严格 JSON。
- 不能返回候选集合之外的 paper_id。
- 推荐理由限制长度。

### 10.3 服务端校验

1. paper_id 白名单。
2. evidence_field 必须存在。
3. evidence_text 必须是对应字段中的短片段或空。
4. year 条件由代码复核。
5. exclude 为 true 时不得评为 high。
6. must 明确 false 时不得评为 high。

### 10.4 修复和回退

- JSON 不合法：修复一次。
- 单批失败：缩小批次重试。
- 关键候选仍冲突：ModelRouter 可选择 Pro。
- 全部失败：使用 reranker 分数并标记核验不可用。

---

## 11. 小阶段 5.8：综合排序

### 11.1 分层而非简单加权

建议先执行等级规则：

1. 排除明确不相关和违反 exclude 的论文。
2. 所有 must 为 true 或部分 unconfirmed 的论文进入主要候选。
3. must 明确 false 的论文只能进入部分相关或剔除。
4. 在同一等级内计算综合分数。

### 11.2 综合分数

可配置示例：

```text
final_score =
  w1 * reranker_score
+ w2 * semantic_score
+ w3 * rrf_score
+ w4 * constraint_score
+ w5 * metadata_quality
+ w6 * recency_score
+ w7 * authority_score
```

规则：

- `constraint_score` 和相关性权重最高。
- `recency_score` 只在相关性相近时起作用。
- `authority_score` 不能让不相关论文上升。
- 所有原始分数先归一化。
- 保存分项分数，便于解释和调试。

### 11.3 近期发表

用户未指定年份时：

- 近期论文可以获得轻微奖励。
- 不得完全压制经典高相关论文。
- 最终结果保留适度时间分布。

## 12. 小阶段 5.9：Coverage Gap Analyzer

### 12.1 输入

- QueryIntent。
- 当前所有核验结果。
- 最终候选数量。
- 每轮新增数量。
- 已执行子查询。
- 来源可用性。
- 当前预算。

### 12.2 输出

```python
class CoverageGap(BaseModel):
    gap_type: str
    constraint: str
    severity: float
    current_match_count: int
    recommended_query_focus: str

class CoverageReport(BaseModel):
    target_count: int
    high_relevance_count: int
    partial_relevance_count: int
    gaps: list[CoverageGap]
    new_valid_count: int
    marginal_gain: float
    should_continue: bool
    stop_reason: str | None
```

### 12.3 规则

优先发现：

- must 条件无匹配。
- 数据集未确认。
- 方法未确认。
- 目标年份内结果不足。
- 某来源缺少覆盖。
- 高相关数量少于目标 20。

## 13. 小阶段 5.10：Query Evolution

### 13.1 生成原则

只针对缺口生成下一轮查询：

```text
原始：LLM time series forecasting
缺口：ETT 数据集
演化：
- "large language model" AND ETTh1 forecasting
- LLM ETTm2 time series prediction
- foundation model ETT benchmark forecasting
```

### 13.2 防重复

- 计算查询指纹。
- 与所有已执行子查询比较。
- 相似度过高时拒绝。
- 每个缺口最多生成配置数量的查询。

### 13.3 放宽策略

只有在严格查询结果不足时，按顺序放宽：

1. 扩展同义词。
2. 放宽 soft 条件。
3. 扩大来源。
4. 不得自动移除 must 或 exclude。
5. 如需放宽硬条件，必须在结果中明确说明，或要求用户确认。

## 14. 小阶段 5.11：多轮搜索控制器

### 14.1 继续条件

同时满足：

- 高相关结果少于 20，或关键 must 覆盖不足。
- 存在可执行的新查询。
- 最新一轮仍有边际收益，或这是第一轮缺口修复。
- 预算未触顶。
- 至少两个来源可用，或一个来源仍有明显价值。

### 14.2 停止条件

- 已获得约 20 篇符合条件论文。
- 关键约束充分覆盖。
- 最新一轮新增高质量论文小于阈值。
- 达到最大轮数。
- API、Token、费用或时间触顶。
- 所有可用查询已执行。
- 外部来源持续失败。

### 14.3 目标数量语义

“20 篇”是目标，不是无限调用的强制保证：

- 若只能找到 12 篇真正符合条件的论文，应返回 12 篇并说明不足。
- 不得用低相关论文凑满 20 篇。

## 15. 小阶段 5.12：文献库语义搜索

### 15.1 写入

收藏论文后：

1. 检查全局 embedding 是否存在。
2. 复用相同向量或在文献库索引添加对应 vector ID。
3. 写 `library_items` 和索引映射。

### 15.2 查询

```text
结构化筛选
→ Query BGE-M3
→ Library FAISS Top-Kx
→ SQLite 读取 PaperRecord 和 LibraryItem
→ 过滤逻辑删除
→ 返回 Top-K
```

### 15.3 删除

- 删除收藏记录。
- 文献事实不删除。
- 文献库索引逻辑删除或定期重建。

- 逻辑删除过滤。

- 排序输出。

### 18.4 LLM Verification

- 合法 JSON。
- 未知 paper_id。
- 虚构 evidence。

- 查询去重。

## 21. 阶段验收条件

- 候选能够从约 100–180 篇压缩到最终高相关集合。
- must 和 exclude 的优先级高于引用数和近期性。
- 近期论文只在相关性相近时获得优势。
- LLM 每个结论有真实字段证据或 `unconfirmed`。
- 未知 paper_id 和虚构证据会被服务端拒绝。
- 多轮搜索能够针对缺口生成新查询。
- 已达到约 20 篇、边际收益不足或预算触顶时正确停止。
- 结果不足时不使用低相关论文凑数。
- FAISS 可由 SQLite 和模型重建。
- BGE、reranker 或 LLM 失败时均有可解释降级路径。
