# 阶段二：多源学术检索

## 1. 阶段目标

本阶段建立统一的学术检索基础设施，完成 OpenAlex、Semantic Scholar、arXiv、PubMed 和 DBLP 的适配器设计，并实现来源级缓存、限流、重试、熔断、降级和调用记录。

完成后，上层业务能够使用统一接口请求多个来源，而不感知具体供应商字段。

本阶段输出的是“来源候选记录”，暂不进行完整的跨来源身份合并、语义排序和 LLM 核验。

---

## 2. 前置条件

- 阶段一完成。
- FastAPI、配置、日志、Redis 和 SQLite 可用。
- `httpx` 已进入 requirements。
- 已获得需要 Key 的来源凭证，并仅写入本地 `.env`。
- 外部 API 具体限制以实现时官方文档为准，所有阈值配置化。

## 4. 小阶段 2.1：来源中间模型

为避免直接把供应商响应传到上层，定义中间模型：

```python
class SourcePaperRecord(BaseModel):
    source: str
    external_id: str
    title: str
    abstract: str | None
    authors: list[SourceAuthor]
    publication_year: int | None
    venue: str | None
    doi: str | None
    arxiv_id: str | None
    pmid: str | None
    source_rank: int | None
    cited_by_count: int | None
    reference_ids: list[str]
    citation_ids: list[str]
    open_access_url: str | None
    raw_metadata: dict[str, Any] | None
```

要求：

- `raw_metadata` 默认不进入 Redis 长期缓存和 SQLite 主表。
- 中间模型字段允许缺失。
- 供应商特殊字段只能保存在 adapter 内或 `raw_metadata`。
- 阶段四再转换为完整 `PaperRecord`。

## 5. 小阶段 2.2：统一 Adapter 协议

建议定义：

```python
class AcademicSourceAdapter(Protocol):
    name: str

    async def search(
        self,
        query: SourceSearchQuery,
        *,
        cursor: str | None = None,
        limit: int = 20,

    async def get_paper(self, external_id: str) -> SourcePaperRecord | None: ...

    async def get_references(
        self,

        *,
        limit: int = 50,
    ) -> list[SourcePaperRecord]: ...

    async def get_citations(
        self,
        external_id: str,
        *,
        limit: int = 50,
    ) -> list[SourcePaperRecord]: ...

    async def health_check(self) -> SourceHealth: ...
```

每个适配器声明 Capability：

```text
SEARCH
DETAIL
REFERENCES
CITATIONS
RELATED
AUTHOR_SEARCH
VENUE_FILTER
DATE_FILTER
```

上层在调用前检查能力，不通过异常猜测能力。

## 6. 小阶段 2.3：统一查询对象

定义 `SourceSearchQuery`：

```python
class SourceSearchQuery(BaseModel):
    text: str
    year_start: int | None = None
    year_end: int | None = None
    authors: list[str] = []
    venues: list[str] = []
    paper_types: list[str] = []
    exclude_terms: list[str] = []
    fields: list[str] = []
```

来源适配器负责将统一查询转换为自身参数。

转换时必须记录：

- 原始统一查询。
- 实际发送的来源查询。
- 被忽略的过滤条件。
- 结果分页信息。

## 7. 小阶段 2.4：共享 HTTP 基础设施

### 7.1 HttpClientFactory

为每个来源创建独立客户端：

- Base URL。
- 默认 Header。
- User-Agent。
- 连接池。
- 超时。
- 代理。
- TLS 校验。

### 7.2 超时

建议拆分：

- connect timeout。
- read timeout。
- write timeout。
- pool timeout。

所有值配置化。

### 7.3 响应处理

统一处理：

- 2xx 成功。
- 400 类参数错误，不重试。
- 401/403 认证错误，不重试并标记来源不可用。
- 404 详情缺失，返回空结果。
- 429 限流，读取 `Retry-After`。
- 5xx 临时错误，可重试。
- 非 JSON 或 Schema 不符合，转换为 `SourcePayloadError`。

### 7.4 日志

记录：

```text
source
endpoint
method
status_code
latency_ms
retry_count
cache_hit
result_count
```

禁止记录完整 Key 和过大的响应体。

## 8. 小阶段 2.5：限流实现

### 8.1 来源级限制

每个来源配置：

```yaml
sources:
  semantic_scholar:
    requests_per_second: 1
    max_concurrency: 1
    timeout_seconds: 20
  openalex:
    requests_per_second: 5
    max_concurrency: 4
```

具体值在部署前根据官方政策重新核验。

### 8.2 算法

建议组合：

- 本进程 `asyncio.Semaphore` 控制并发。
- Redis 滑动窗口或 Token Bucket 控制多进程总频率。
- 429 后写入来源冷却时间。

接口：

```python
class SourceRateLimiter:
    async def acquire(self, source: str) -> None: ...
    async def penalize(self, source: str, retry_after: float | None) -> None: ...
```

Redis 不可用时回退到本地限流，并输出 WARNING。

## 9. 小阶段 2.6：重试与熔断

### 9.1 重试

只重试：

- 网络连接错误。
- 超时。
- 429。
- 502、503、504。

不重试：

- 查询参数错误。
- 认证错误。
- 明确的无权限错误。

采用指数退避和随机抖动：

```text
delay = min(max_delay, base_delay * 2^attempt) + jitter
```

### 9.2 熔断器

每个来源独立维护：

- `CLOSED`
- `OPEN`
- `HALF_OPEN`

打开条件和恢复时间配置化。

熔断时：

- 不发起请求。
- 返回来源降级状态。
- 其他来源继续执行。

## 10. 小阶段 2.7：Redis 缓存

### 10.1 缓存键

```text
source
endpoint
adapter_version
normalized_query
filters
cursor
limit
selected_fields
```

序列化后计算 SHA-256。

示例：

```text
ScholarFlow:source:cache:openalex:search:v1:<hash>
```

### 10.2 TTL

建议分类配置：

- 搜索结果：6–24 小时。
- 论文详情：7–30 天。
- 引用关系：1–7 天。
- 失败负缓存：1–5 分钟。

### 10.3 Cache Stampede

相同缓存键：

1. 查询 Redis。
2. 未命中时尝试获取锁。
3. 获取锁的请求回源。
4. 其他请求短暂等待后再次查缓存。
5. 锁超时后允许有限回源。

## 11. 小阶段 2.8：OpenAlex Adapter

### 11.1 功能

- Works 搜索。
- 年份过滤。
- 作者、机构、venue 和论文类型过滤。
- 论文详情。
- DOI、开放获取和引用数。
- 引用、被引 ID。
- 游标分页。

### 11.2 字段选择

只请求当前阶段需要的字段，减少响应大小。

### 11.3 查询转换

- 普通文本放入搜索参数。
- 硬年份条件放入 filter。
- 多个作者和 venue 需要明确 AND/OR 策略。
- 不支持的排除条件交给后续规则过滤。

### 11.4 结果映射

明确处理：

- 缺摘要。
- 倒排索引形式摘要的还原。
- DOI URL 规范化前的原值保存。
- 作者顺序。
- Open Access URL。

## 12. 小阶段 2.9：Semantic Scholar Adapter

### 12.1 功能

- 关键词搜索。
- 论文详情。
- 摘要。
- 引用和被引。
- 相关论文。
- 批量论文详情。

### 12.2 调用策略

- 搜索阶段只获取必要字段。
- 进入候选池后批量补全详情。
- 引用扩展只针对少量高相关种子论文。
- 严格遵守保守限流。

### 12.3 错误处理

- 429 写负缓存。
- 批量接口中单条缺失不应让整批失败。
- 返回顺序必须与请求 ID 映射，不能仅依赖位置。

## 15. 小阶段 2.12：DBLP Adapter

### 15.1 适用范围

- 计算机会议。
- 作者检索。
- venue 精确约束。

### 15.2 功能

- publication 搜索。
- author 搜索。
- venue 和年份筛选。
- DBLP key 保存。

### 15.3 注意事项

- DBLP 摘要覆盖有限，不能作为唯一来源。
- 主要用于补全会议、作者和出版信息。
- 后端论文检索固定传递 `c=0` 关闭自动补全，因为该结果不进入统一论文记录或排序，避免泛词查询额外增加来源计算负担。

## 17. 小阶段 2.14：Search Service

建议接口：

```python
class MultiSourceSearchService:
    async def search(
        self,
        route_plan: SourceRoutePlan,
        *,
        run_id: str,
    ) -> MultiSourceSearchResult: ...
```

执行步骤：

1. 为每个来源创建协程。
2. 通过 `asyncio.gather(..., return_exceptions=True)` 并行执行。
3. 独立记录来源成功或失败。
4. 汇总结果，不做跨来源去重。
5. 返回来源统计和降级信息。

禁止一个来源异常取消全部来源。

## 19. 测试规划

### 19.1 Adapter 契约测试

每个来源使用固定 mock 响应测试：

- 正常搜索。
- 空结果。
- 缺少摘要。
- 分页。
- 429。
- 5xx。
- 超时。
- 非法响应。
- 部分字段缺失。

### 19.2 缓存测试

- 首次未命中。
- 第二次命中。
- TTL 过期。
- 负缓存。
- 锁竞争。
- Redis 不可用。

### 19.3 限流测试

使用虚拟时钟或短窗口验证，不等待真实秒级时间。

### 19.4 在线 Smoke Test

由用户手动执行，默认每个来源只请求少量结果，避免浪费额度。

当前已接入的学术来源为 OpenAlex、Semantic Scholar、arXiv 与 DBLP；Tavily 仅用于补充网页发现，不纳入学术来源 smoke 测试。执行前由用户确认本地 `.env` 中相应配置可用，然后在 PowerShell 中显式开启一次性网络测试：

```powershell
$env:SCHOLARFLOW_RUN_ONLINE_SOURCE_SMOKE_TESTS='true'
pytest -m online backend/tests/test_online_academic_source_smoke.py
Remove-Item Env:SCHOLARFLOW_RUN_ONLINE_SOURCE_SMOKE_TESTS
```

测试仅使用 `Transformer` 查询，并将每个来源的召回限制为一篇；OpenAlex 仍要求配置 API Key，Semantic Scholar 的实际认证与可用性由当前配置和供应商策略决定。常规 `pytest` 不会调用任何外部 API。

## 22. 阶段验收条件

- 同一查询能够从 OpenAlex、Semantic Scholar 和一个动态来源返回候选。
- 三个动态来源均具备可调用实现或明确的完成状态。
- 供应商原始字段不会泄漏到上层业务。
- 一个来源失败时，其他来源仍成功返回。
- 缓存、限流、重试和熔断均有测试。
- 429、超时和 5xx 能被正确分类。
- 重复查询可以命中 Redis。
- 所有调用都有结构化日志和 usage 记录。
- 真实 API Key 不出现在日志、响应和 Git 中。
