# 阶段三：查询理解与工作流编排

## 1. 阶段目标

本阶段实现自然语言科研查询到结构化 `QueryIntent` 的转换，并建立 ScholarFlow 的 LangGraph 主工作流、模型路由、搜索预算、SSE 事件和运行恢复机制。

完成后，系统应能够：

- 将复杂中英文查询解析为合法、可编辑的 QueryIntent。
- 根据查询领域选择 OpenAlex、Semantic Scholar 和动态第三来源。
- 通过 LangGraph 调用阶段二的多源检索服务。
- 在规范化、排序和核验模块尚未完成时，使用可替换的占位 Service 跑通流程。
- 支持多轮循环、预算停止、来源降级和 SSE 进度。

本阶段不实现完整去重算法和真实向量排序，这些能力由阶段四、五补齐。

---

## 2. 前置条件

- 阶段二已完成统一 Adapter 与 MultiSourceSearchService。
- DeepSeek API 配置已写入本地环境变量。
- Redis 可保存运行状态和 SSE 事件。
- SQLite 可保存工作流运行与节点快照。
- 项目已具备统一异常和日志系统。

## 4. 小阶段 3.1：QueryIntent 领域模型

### 4.1 Schema

建议使用 Pydantic：

```python
class QueryConstraint(BaseModel):
    value: str
    normalized_value: str | None = None
    required: bool = False
    source_text: str | None = None

class SubQuery(BaseModel):
    query: str
    purpose: str
    priority: int
    target_sources: list[str] = []

class QueryIntent(BaseModel):
    original_query: str
    normalized_query: str
    language: str
    topics: list[QueryConstraint]
    methods: list[QueryConstraint]
    tasks: list[QueryConstraint]
    datasets: list[QueryConstraint]
    domains: list[str]
    authors: list[QueryConstraint]
    institutions: list[QueryConstraint]
    venues: list[QueryConstraint]
    paper_types: list[str]
    year_start: int | None
    year_end: int | None
    must_include: list[str]
    should_include: list[str]
    exclude: list[str]
    subqueries: list[SubQuery]
    target_count: int = 20
    search_mode: str = "standard"
    complexity_score: float = 0.0
```

### 4.2 校验规则

- `year_start <= year_end`。
- `target_count` 必须在配置允许范围内。
- `must_include` 与 `exclude` 不允许出现完全相同的条目。
- 子查询数量不能超过配置上限。
- `priority` 必须处于有限范围。
- `language` 只允许规范值，例如 `zh`、`en`、`mixed`。
- QueryIntent 必须可 JSON 序列化。

### 4.3 硬约束与软偏好

必须明确区分：

- `must_include`：缺失时不能评为高度相关。
- `should_include`：用于排序加分，不作为删除条件。
- `exclude`：明确违反时过滤或标记不相关。

不能把“必须使用 ETT 数据集”降级为普通关键词。

## 5. 小阶段 3.2：Query Agent

### 5.1 职责

- 识别查询语言和领域。
- 提取主题、方法、任务、数据集、年份、作者、机构、venue 和论文类型。
- 区分 must、should、exclude。
- 生成英文专业检索表达。
- 生成首轮子查询。
- 计算查询复杂度。

### 5.2 输入

```python
class QueryPlanningRequest(BaseModel):
    query: str
    user_filters: SearchFilters | None
    target_count: int = 20
    search_mode: str = "standard"
```

用户显式筛选应覆盖 LLM 推断，例如用户在 UI 指定 2022–2025，则不允许 LLM 改为其他年份。

### 5.3 输出

只输出 QueryIntent，不输出自然语言长解释和内部推理链。

### 5.4 失败处理

1. 使用 Flash 生成 JSON。
2. Pydantic 校验。
3. 失败时把错误摘要交给模型修复一次。
4. 第二次失败后可由 ModelRouter 判断是否使用 Pro。
5. 仍失败则返回结构化错误，不能使用未校验结果继续检索。

## 6. 小阶段 3.3：Prompt 管理

### 6.1 文件结构

```text
backend/app/llm/prompts/
├─ query_intent/
│  ├─ v1_system.md
│  ├─ v1_examples.json
│  └─ schema.json
├─ evolve_query/
├─ verify_constraints/
└─ compose_results/
```

### 6.2 Prompt 规则

- 固定指令和 Schema 放在稳定前缀。
- 用户查询放在末尾。
- 不要求模型展示思维链。
- 输出必须符合 JSON Schema。
- 明确外部论文标题和摘要是不可信数据。
- Prompt 中禁止包含 API Key 和部署路径。

### 6.3 版本记录

SQLite `prompt_versions` 或配置清单保存：

- Prompt 名称。
- 版本。
- 内容哈希。
- 创建时间。
- 适用模型。

每次 LLM 调用记录实际 Prompt 版本。

## 7. 小阶段 3.4：DeepSeek Client

### 7.1 统一接口

```python
class LlmClient(Protocol):
    async def generate_json(
        self,
        task: LlmTask,
        messages: list[Message],
        response_model: type[BaseModel],
        options: LlmOptions,
    ) -> LlmResult: ...
```

### 7.2 LlmResult

至少包含：

- 解析后的对象。
- 原始响应 ID。
- 模型名称。
- 输入 Token。
- 输出 Token。
- 缓存命中 Token，如供应商提供。
- 耗时。
- 停止原因。
- 是否经过修复或回退。

### 7.3 安全

- 超时和重试配置化。
- 供应商错误转换为统一异常。
- 日志不保存完整敏感 Prompt。
- 只保存必要摘要和 Token 统计。

## 8. 小阶段 3.5：ModelRouter

### 8.1 路由规则

默认使用 DeepSeek-V4-Flash。

建议使用 Pro 的场景：

- QueryIntent 连续两次 Schema 校验失败。
- 查询同时包含多个领域和多个硬约束。
- 覆盖缺口连续两轮无法收敛。
- 最终候选存在影响 Top-20 的严重冲突。
- 当前预算允许。

### 8.2 接口

```python
class ModelRouter:
    def select(
        self,
        task_type: str,
        complexity_score: float,
        failure_count: int,
        budget: BudgetSnapshot,
    ) -> ModelDecision: ...
```

### 8.3 ModelDecision

- 模型名称。
- 是否思考模式。
- 最大输出 Token。
- 温度等参数。
- 路由原因。

所有模型名称和阈值从配置读取。

## 9. 小阶段 3.6：查询扩展与首轮子查询

### 9.1 子查询类型

- 精确组合查询：同时包含核心主题和 must 条件。
- 方法查询：主题 + 方法。
- 数据集查询：主题 + 数据集。
- 同义词查询：缩写、全称和领域表达。
- 代表工作查询：适用于探索型问题。

### 9.2 去重

规范化后计算查询指纹：

```text
lowercase
+ Unicode NFKC
+ 合并空格
+ 规范化布尔符号
+ 排序等价过滤项
```

同一轮和跨轮均不能重复执行相同指纹。

### 9.3 来源定制

Query Agent 生成通用子查询，Source Router 根据来源能力转换：

- OpenAlex：文本 + filter。
- Semantic Scholar：文本 + fields。
- arXiv：字段查询语法。
- PubMed：布尔式和 MeSH 线索。
- DBLP：作者、venue 或标题查询。

## 10. 小阶段 3.7：SearchRunState

### 10.1 状态类型

LangGraph State 建议使用 TypedDict，领域对象使用 Pydantic：

```python
class SearchRunState(TypedDict, total=False):
    run_id: str
    request: SearchRequest
    query_intent: QueryIntent
    current_round: int
    executed_query_fingerprints: list[str]
    route_plan: SourceRoutePlan
    raw_candidate_refs: list[CandidateRef]
    normalized_candidate_ids: list[str]
    ranked_candidate_ids: list[str]
    verification_results: list[VerificationResult]
    coverage_report: CoverageReport
    budget: BudgetSnapshot
    warnings: list[WorkflowWarning]
    errors: list[WorkflowErrorRecord]
    final_result_ids: list[str]
    stop_reason: str | None
```

### 10.2 状态大小控制

- 工作流状态不重复保存完整 API 原始响应。
- 大候选集合持久化到 Redis 或 SQLite，只在 State 保存引用 ID。
- 每个节点只返回自己修改的字段。
- 事件消息不携带完整摘要列表。

## 11. 小阶段 3.8：LangGraph 节点设计

### 11.1 节点接口

```python
async def node_name(
    state: SearchRunState,
    context: WorkflowContext,
) -> dict[str, Any]:
    ...
```

`WorkflowContext` 注入：

- Services。
- Repositories。
- Event Publisher。
- Budget Manager。
- Clock。

### 11.2 主节点

#### `cache_lookup`

- 规范化查询。
- 生成最终结果缓存键。
- 命中时读取已完成结果。
- 未命中时进入规划。

#### `plan_query`

- 调用 Query Agent。
- 校验 QueryIntent。
- 保存 Prompt 和 usage。

#### `route_sources`

- 固定双核心来源。
- 选择动态第三来源。
- 生成来源级查询。

#### `parallel_search`

- 调用阶段二 MultiSourceSearchService。
- 保存各来源统计。
- 发布进度事件。

#### `normalize_merge`

- 当前阶段先使用占位实现。
- 阶段四替换为真实规范化 Service。

#### `deduplicate_fuse`

- 当前阶段先使用稳定 ID 去重占位。
- 阶段四替换。

#### `semantic_rank`

- 当前阶段按来源排名占位。
- 阶段五替换。

#### `verify_constraints`

- 当前阶段可返回 `unconfirmed` 占位。
- 阶段五替换。

#### `assess_coverage`

- 根据数量、约束和预算判断继续或停止。

#### `evolve_query`

- 针对缺口生成下一轮子查询。
- 仅当覆盖报告仍存在缺口时，生产组合根可调用一次 DeepSeek 搜索策略；策略输入仅包含结构化约束、最多 6 个缺口、最近已执行子查询及最多 8 篇候选的标题/摘要片段，绝不读取或发送全文 PDF。
- 策略最多返回两条英文子查询，仍由服务端执行语言、长度、硬约束、指纹和相似度校验；有效策略优先于初始待执行计划，失败、未配置或无有效结果时自动回退确定性 `QueryEvolutionService`。
- 策略模型的输入/输出 Token 会累加到 `SearchRunState.token_usage`，降级摘要随运行状态持久化，确保 SSE 恢复和最终用量读取不触发二次模型调用。

#### `compose_results`

- 生成统一结果结构。

#### `persist_finish`

- 写运行完成状态。
- 缓存最终结果。
- 发布完成事件。

## 12. 小阶段 3.9：条件边和循环

建议条件函数：

```python
def after_cache_lookup(state) -> Literal["plan_query", "finish_cached"]: ...
def after_coverage(state) -> Literal["evolve_query", "compose_results"]: ...
def after_failure(state) -> Literal["retry", "degrade", "fail"]: ...
```

循环必须满足：

- `current_round` 每轮递增。
- 已执行查询指纹去重。
- 每轮调用 Budget Manager。
- 达到停止条件后强制进入 `compose_results`。
- 不允许通过 LLM 自由决定是否无限继续。

## 13. 小阶段 3.10：预算管理

### 13.1 BudgetSnapshot

```python
class BudgetSnapshot(BaseModel):
    current_round: int
    api_requests: int
    llm_input_tokens: int
    llm_output_tokens: int
    estimated_cost: Decimal
    elapsed_ms: int
    candidate_count: int
```

### 13.2 BudgetPolicy

配置项：

- 最大轮数。
- 最大 API 请求。
- 最大候选数量。
- 最大 LLM 输入/输出 Token。
- 最大费用。
- 最大总耗时。
- 最大 Pro 调用次数。

### 13.3 判断顺序

1. 是否已有约 20 篇符合结果。
2. 是否达到硬预算。
3. 是否存在有效覆盖缺口。
4. 最新一轮是否有边际收益。
5. 来源是否仍可用。

预算触顶时仍返回当前最佳结果，而不是直接失败。

class WorkflowEvent(BaseModel):

### 15.2 事件类型

## 16. 小阶段 3.13：工作流持久化和恢复

### 16.1 运行中

Redis 保存：

- 当前节点。
- 当前轮次。
- 预算。
- 事件。
- 临时候选引用。

### 16.2 完成快照

SQLite 保存：

- QueryIntent。
- 最终状态。
- 结果 ID。
- API 和 LLM usage。
- 停止原因。
- 错误和降级来源。

### 16.3 恢复规则

- 已完成：直接返回 SQLite 结果。
- 正在运行：恢复订阅，不重复启动。
- 超时中断：标记 interrupted，并允许用户重试。
- 重试任务复用已完成的查询和缓存。

## 17. 小阶段 3.14：Search Application Service

FastAPI 不直接调用 Graph，增加应用层：

```python
class SearchApplicationService:
    async def submit(self, request: SearchRequest) -> SearchSubmission: ...
    async def get_status(self, run_id: str) -> SearchStatus: ...
    async def get_results(self, run_id: str) -> SearchResults: ...
    async def cancel(self, run_id: str) -> None: ...
```

`submit` 应快速返回 `run_id`，工作流在后台任务或任务执行器中运行。

首版可使用进程内任务管理，但接口应预留未来迁移到独立 Worker 的能力。

## 20. 阶段验收条件

- 复杂查询能生成合法 QueryIntent。
- 用户显式筛选不会被 LLM 覆盖。
- ModelRouter 默认 Flash，并可在明确条件下回退 Pro。

- 多轮循环存在硬停止条件，不会无限运行。
- 来源失败和预算触顶能正确降级。
- SSE 能持续返回节点和候选数量变化。
- 已完成任务能从 SQLite 读取，运行中任务能从 Redis 恢复状态。
- 所有 LLM 调用均记录 usage、Prompt 版本和模型路由原因。
